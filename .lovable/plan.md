# Move all file storage to Cloudflare R2

## What exists today

Files in your app live in five storage buckets on the current backend:

| Bucket | Used by |
| --- | --- |
| `avatars` | profile photos (Settings) |
| `workspace-logos` | workspace branding |
| `support-attachments` | support ticket attachments |
| `blog-media` | blog / admin media library |
| `review-media` | testimonial media |

CSV exports (leads, campaigns, warmup pool, contacts) are **not** stored anywhere today — they are generated in the browser and downloaded directly. Invoices, reports and PDF exports do not exist as stored files yet. So the real migration surface is the five buckets above, plus a new file service that all future exports/imports/invoices/reports plug into.

## One deviation from your spec

This project runs on TanStack Start, which has its own server runtime. Presigned URLs will be generated by a **server endpoint in this app** rather than a separate Edge Function — same behaviour (auth check, ownership check, rate limit, short-lived URL), one less moving part, and files still never pass through the backend. Everything else follows your spec exactly.

## What gets built

**1. R2 client + presign endpoints**
- Small SigV4 signer (no AWS SDK — keeps the worker bundle edge-safe) talking to `https://{R2_ACCOUNT_ID}.r2.cloudflarestorage.com/munchreach-files`.
- `requestUpload` — auth required, validates the requested key prefix belongs to the caller, enforces 50MB max and an allow-list of MIME types, returns a presigned PUT URL (5 min) plus a pending `files` row.
- `confirmUpload` — marks the row `ready` and records real size.
- `requestDownload` — auth required, only for rows the caller owns (or workspace/admin-visible ones), returns a presigned GET URL (5 min).
- `deleteFile` — owner-only, removes the R2 object and the row.
- Rate limit: 60 presign requests per user per minute, stored in the existing rate-limit table pattern.

**2. Key structure** exactly as you specified:
`imports/{user_id}/{uuid}.csv`, `exports/{user_id}/{uuid}.csv`, `invoices/{user_id}/{invoice_id}.pdf`, `reports/{user_id}/{uuid}.pdf`, `campaigns/{user_id}/{campaign_id}/{uuid}.csv`, `leads/{user_id}/{uuid}.csv`, `tmp/{user_id}/{uuid}.tmp`, plus `avatars/{user_id}/…`, `workspace-logos/{user_id}/…`, `support/{user_id}/…`, `media/{user_id}/…` for the existing buckets.

**3. `files` metadata table**
`id, user_id, workspace_id, type, r2_key, size, mime_type, status, created_at, updated_at, expires_at`. Owner-scoped access rules; anything written under `tmp/` gets `expires_at = now + 24h` so your R2 lifecycle rule can sweep it.

**4. Frontend rewiring**
Shared `uploadFileToR2(file, type)` / `getFileUrl(fileId)` helpers. Every current upload and image-display path is switched over: Settings avatar, Workspace logo, Support attachments (user + admin views), Admin media library, testimonial media, and the public media route. CSV export helpers get an optional "save to R2" path so lead/campaign exports produce a stored, re-downloadable file.

**5. One-time migration**
An admin-only migration endpoint that lists every object in the five old buckets, streams each into the matching R2 key, writes a `files` row, and reports a per-bucket summary. It is resumable, skips already-migrated keys, and **deletes nothing** from the old buckets.

**6. Safe-to-delete report**
After you run the migration and confirm counts match, I'll tell you exactly which buckets/paths are clear to remove — expected answer: all five buckets, once every migrated row shows `ready` and the app reads only R2.
