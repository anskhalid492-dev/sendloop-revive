- Campaign Leads pages join `leads` only when a lead-column filter is active (src/lib/campaign-leads-page.ts); otherwise page recipients alone and load that page's leads by id, because the full join+sort on every refresh was the top DB cost.
- Campaign queue mode (src/lib/campaign-queue.server.ts) wraps the existing runCampaign dispatcher as per-campaign `campaign_tick` jobs and shares the legacy `campaign_scheduler_lease`, so sending rules live in one place and legacy/queue can never overlap; crash recovery (shared by legacy and queue via `recoverUnprovenProcessing`) uses the `last_error` send-phase marker (src/lib/campaign-send-phase.ts): rows proven never handed to the provider are requeued, rows that reached or may have reached the provider are held as outcome-unknown and never resent, because an interrupted SMTP call may already have been accepted.
- Mailbox queue mode (src/lib/mailbox-queue.server.ts) wraps the existing `pollMailbox` as per-mailbox `mailbox_poll` jobs selected by the shared `loadPollableMailboxes`, shares the legacy `mailbox_poll_lease`, and never claims more jobs per run than it selected, so IMAP workload cannot exceed legacy.
- Mailbox poll runs only start new mailbox work within a start budget (legacy ~20s; queue ~10s with a 4-slot pool refilled per freed slot) and never abort in-flight IMAP reads; the queue run also stops WAITING at a ~24s deadline and hands still-running jobs back to the queue (attempt not counted), because valid reads can exceed the ~30s platform kill, a killed run leaves the shared lease held, and the mailbox cursor only advances after messages are handled.
- Warmup queue mode (src/lib/warmup-queue.server.ts) wraps the existing warmup engine (shared `scheduleWarmupDue`, `claim_warmup_jobs`, `processJob`) in one `warmup_tick` background job per run, shares the legacy `warmup_runner_state` lease, sends sequentially within a ~20s start budget, and is at-most-once on crash (stale queue-owned `processing` sends are failed, never resent), so legacy limits and volume stay authoritative.
- Transactional queue mode (src/lib/transactional-queue.server.ts) wraps the existing engine's `deliverTransactional` as one `transactional_tick` job per minute, shares the legacy `transactional_runner_lease`, marks rows claimed→provider_call before contacting the provider, only begins a provider call before a cutoff of platform limit minus Resend's worst-case send minus a post-send reserve (system email skips the optional RFC Message-ID read), handing late rows back untouched, and is at-most-once: stale or timed-out sends become `outcome_unknown` (never resent), because a crashed Resend call may already have been delivered.
- `acquireWorkerLease` creates missing lease rows with upsert ON CONFLICT DO NOTHING, never a plain insert, because a held lease otherwise raised a duplicate-key error on every cron tick.
- Admin Warmup Analytics (src/lib/warmup-analytics*.ts) aggregates only the engine's `warmup_daily_stats` rollup server-side behind assertSuperAdmin, because it is already one row per mailbox per UTC day and needs no new table or raw-email reads.
- Visual automation workflows are stored as ONE `automation_steps` row (config.type `workflow.graph`, tree in config.workflow) and executed by `executeWorkflow` (src/lib/workflow-runner.ts) with one run-step per hop; legacy linear automations keep the old engine path, because this needs no schema change and keeps existing automations unchanged.
- Automation events carry a `chain` (depth + automation ids); `automationsAllowedByChain` blocks self re-triggers and chains deeper than MAX_CHAIN_DEPTH, because action-emitted events could otherwise loop forever.
- Workflow "Test workflow" dry runs use the pure `simulateWorkflow` (src/lib/workflow-simulator.ts, no IO) behind `runWorkflowSimulation`, which reads only through the caller's RLS client with explicit workspace filters and writes nothing; the real action layer also refuses any run whose metadata has `simulation: true`, because dry runs must never be able to cause side effects.
- Triggers with no server emitter are marked `available: false` in TRIGGERS and are hidden from pickers and rejected at activation, so a workflow can never be live on a dead trigger.
- `email.sent` / `campaign.completed` automation events are emitted via src/lib/automation-emit.server.ts only after a confirmed sent row / an actual active→completed flip, with stable keys (`email.sent:<message id>`, `campaign.completed:<campaign id>`) so the existing idempotency index absorbs duplicates.
- AI Decision is idempotent per hop: a completed hop reuses its stored path, an interrupted (`running`) hop takes the fallback without re-asking, and AI replies default to draft with mandatory safety rules forcing draft/blocking, because AI calls cost money and must never send twice or on uncertainty.
- AI Sales Agent workspace settings live in `platform_settings` key `ai_sales_agent:<workspaceId>`, read/written only via membership-checked server functions, because no schema change was needed.
- AI Sales Agent admin monitoring aggregates only `automation_run_steps` AI-step outputs (provider `munchreach`) server-side behind assertSuperAdmin with bounded paged reads, and every AI reply passes `replyDelivery` before sending, because customer-key AI must never be counted and auto-send must fail closed.
- Admin → Campaigns classifies every message through `src/lib/admin-campaign-monitor.ts` (unknown outcome first, then bounced, sent, failed) and reads history with `fetchAllByIds`, because KPI cards, table and drawer must agree and the 1,000-row page limit silently truncated counts.
- Email outcome classification (bounced/failed/delayed/unknown) lives only in src/lib/email-outcome.ts; dsn-parse, dispatch fail(), delivery events and retry rules delegate to it, because separate per-path rules drifted and mislabelled sender-side refusals as bounces.
- Campaign provider calls start only before a cutoff (platform limit − relay send timeout − reserve, src/lib/delivery-lifecycle.ts), use a per-call relay timeout, and skip a mailbox for the rest of the run after a transport timeout, because calls running past the ~30s worker kill were the source of held outcome-unknown rows.
- IMAP bounce reports are matched to the exact send first via the quoted original Message-ID / warmup token (a report read in the sending mailbox is that warmup job's bounce, deduped by a per-job external_id), with recipient-address matching only as a fallback, because warmup reports were previously swallowed as "foreign" arrivals.
